# Development Constraints & Quality Standards

To ensure the reliability of the financial data engine and prevent regressions, all work in this repository must adhere to the following rules:

## 1. Incremental Progress (Bite-Sized)
- We build up code slowly and in **small bite-sized pieces**.
- **The 30-Line Rule**: If a proposed change involves more than approximately 30 lines of code, stop and explain the necessity of the volume. We prefer multiple smaller, verifiable steps over large monolithic updates.

## 2. Layered Architecture
- We build functionality **layer by layer**.
- Lower layers (Data Ingestion, Schema Validation) must be thoroughly understood and verified before adding higher-level logic (Maintenance Loops, Aggregations).

## 3. Strict Verification
- **Test Before Proceeding**: Every logical change must be tested (e.g., running the specific cell with sample tickers) before moving to the next piece of functionality.
- **Data Integrity Safety**: Never implement batch-level deletions or `dropna` operations without first inspecting the impact on a subset of data. Permanent data changes must be preceded by a verify/dry-run step.

## 4. Stability Over Velocity
- If code becomes a "hot mess," we stop, simplify, and revert to the last known stable state of that layer.
- Reliability of the database is the primary KPI; scraping speed and volume are secondary.

## 5. Contract-First Strategy
- For complex architectural changes, favor a **"Spec First, Code Second"** approach.
- Always prompt the agent to outline the inputs, outputs, and internal state changes (pseudocode) before any implementation is allowed.
- Do not proceed with code generation until the user has explicitly approved the design.

## 6. Question vs. Instruction
- A clarifying question from the user is **never** an instruction to modify code.
- Clarifications and "What if?" scenarios must be answered **conceptually** first.
- **Rule of No Unsolicited Refactoring**: Even if you spot an optimization or a bug while answering a question, you must **propose** the fix and wait for explicit approval. Never "sneak in" improvements or refactors alongside a requested task.
